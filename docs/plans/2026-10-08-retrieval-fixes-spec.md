# 扩展抽样问题修复 spec

日期：2026-10-08。承接 [扩展抽样报告](../verification/2026-10-08-expanded-sample.md)，根据已知失败设计修复，评测协议在预测前冻结。实现及部署结果另见本轮验收报告。

## 问题与目标

1. 短信登录防重复发送的已知题是 PROJECT，规划器将自然语言“场景题”变成 SCENARIO SQL 硬筛选，导致候选池之前丢题。SEARCH 的模型推断题型应作为语义意图；只有可追溯的显式筛选或可信继承范围才能成为 SQL 题型限制。显式 null 清除和跨话题切换必须正确处理。
2. 对象及任务证据都能逐字引用，但仍返回泛 Agent 评分、SFT、搜索、死循环或反思题。证据真实并不等于相关。重排必须同时判别对象层级和任务层级，区分同任务、紧密子任务、覆盖该目标的全链路诊断、泛父话题和相邻任务。
3. 不通过删掉有效结果提高精度：保留工具输出诊断、全链路定位、工具失败重试降级及明确 Function Calling 可靠性等紧密子任务；广义 Agent/Harness 查询仍能返回合理架构模块。

## 实现边界

- 不按题 ID、短信关键词或本次弱例黑名单修复；不改语料及任务分类，不降低旧质量门槛。
- LIST/STATS/NEXT 的精确 SQL 范围、显式 UI 筛选、历史重检、请求幂等、澄清、取消和流式事件均保持各自契约。
- 相关性规则建立新 reranker 版本，保留旧源码及提示词 hash。主机校验引文与关系组合；语义判断仍由模型承担，不能把字符串校验解释成相关性证明。

`after-v2` 在8个完成请求中出现5个精排 `ValidationError`。这些请求虽然HTTP 200，但核验不可用、结果为空，按服务失败计数。停止后第9轮保留PENDING；该轮不是正式完整对照，不与后续结果拼接。候选尚未部署到8000。

三次单独搜索重放均未复现字段错误；旧日志只保留异常类名，无法还原具体失效字段。因此不把枚举混用、缺字段或截断写成已证明原因。r12保持原结构和相关性阈值，明确完整JSON/必填字段/合法枚举要求，增加不含输入内容的限长校验路径及类型诊断；不增加重试、不放宽结构、不扩大模型预算。

使用新目录 `after-v3` 重新执行同一23轮协议，与完整 `before-v2` 比较；两条宽查询另存 `after-guards-v3`。r11原始输出、8轮文本审核、中断状态和3次探针均保留。新结果必须同时报告服务完成率、相关性及有效题丢失，不能只比较非空返回精度。诊断重放是新search-only请求，不作为原请求复现或性能对照。

## 执行修订：r12 的确切字段失败与任务阶段

`after-v3` 最终保留9个完成请求及1个PENDING；其中SYN与缓存一致性两轮HTTP 200但核验不可用。新增安全日志首次定位到 `ValidationError@r[1].focus_relation:literal_error+1`，输出3211 tokens，未达到6144输出上限。非法枚举的具体值未捕获；不能据此断言是哪个字符串，也不能倒推r11的具体错误。

r12文本审核另发现调用超时、阻塞、重试及入参处理被混作工具输出内容质量诊断。r13将重叠的relation/scope四分类字段简化为对象scope、任务scope两轴，由host派生兼容关系及grade；维持逐字引文、完整候选集合、严格枚举及预算，不猜测修补非法值。语义规则补足对象与动作不能互相代替、输出内容质量与调用可用性两个阶段的区别，保留覆盖目标的全链路诊断及宽主题合理子模块。

正式完整对照改为 `before-v2` → `after-v4`，宽查询另存 `after-guards-v4`。r11/r12均为开发失败候选且未部署8000；旧目录不覆盖、不拼接。协议及文本判分标准不变，但提示词已使用这些开发失败进行修订，结论只能说明已曝光开发样本上的效果，不是独立泛化评测。

## 执行修订：r13 失败与 r14 候选隔离

r13保留7轮完成、1轮PENDING；支付及缓存核验失败，安全码分别定位到 `object_scope:literal_error+3` 与 `object_scope:literal_error+4`。首条团购库存耗尽返回10题，仅1题相关、8题邻近、1题无关。失败版本未部署主服务。原提示词允许有限库存业务相互扩展，未限定只用于宽系统设计，造成具体“库存耗尽”混入“防超卖、抢票、锁单”等另一故障/任务。

r14把宽设计子模块与具体故障任务分开，并让query证据覆盖实际限定对象/现象。负类区分NONE（明确无关）与UNKNOWN（证据不足），两者均不准入；旧非法字面值未被捕获，不能称已证明为NONE。

模型仍接收完整strict schema。host先严格验证全局意图字段、引文及当前候选ID精确排列，再逐条严格校验候选。单个身份确定的坏候选隔离为 `INVALID_SCHEMA`，不会猜测/映射其非法值，也不会混进返回结果；全局或候选身份错误仍整轮失败。存在坏候选时显式标记 `candidate_verification_status=PARTIAL`、`invalid_candidate_count` 与 `rerank_status=COMPLETED_PARTIAL`。非空的已核验结果可带“不完整”警告交付；空集且有坏候选必须为UNAVAILABLE，不得声称无匹配。操作遥测另记 `PARTIAL_SCHEMA_REJECTED:n`，不能把交付成功写成零结构异常或全池核验通过。

先在 `pilot-r14` 对团购、工具质量、缓存、短信4个已知失败目标做开发诊断，协议在预测前保存；不并入正式23轮。通过后以 `before-v2` → `after-v5` 为完整对照，宽查询为 `after-guards-v5`，业务版本在该阶段固定。部署只覆盖query_service、harness、reranker、elasticsearch四后端文件，保留其余17个已登记文件及现有页面。所有失败候选、探针及pilot成本另列，语义裁决标准不变。

## 执行修订：r14 诊断未过与 r15 范围复核

r15在第一阶段严格通过的候选上增加范围critic，只接收原query及候选题干，不提供首判分数、关系或引文。返回 `keep` 布尔与简短原因；最终集合必须同时通过首阶段引文/范围契约及范围复核，不新增首阶段以外候选。首阶段无通过项时不增加调用。范围复核必须排除依赖额外业务成因、缺失子对象、不同任务阶段及缺少上下文的题；明确的核心子任务、工具输出全链路定位仍允许。

两阶段分别通过原Linux共享门、原90秒请求期限及6次总调用预算，分别持久化RERANK与RERANK_VERIFY操作和用量，零模型重试。第二阶段全局/ID异常失败不得回退首阶段；单条身份确定的结构异常仍严格隔离并显式PARTIAL。复核是一条额外模型操作，效果、失败、延迟及token代价必须一起报告；使用同模型别名的不同提示词，不称独立模型或人工审核。
