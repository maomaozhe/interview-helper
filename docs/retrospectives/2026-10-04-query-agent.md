# 查询 Agent 实施复盘与面试讲述

日期：2026-10-04。只记录本项目实际问题、处理与证据；完整故障过程在 [问题日志 Q01–Q10](../../md/issue.md)，部署与实测在 [报告](../plans/2026-10-04-open-system-one-deployment.md)。下列第一人称提纲描述实际工程工作，讲述时按自己能够解释和复现的范围使用。

2026-10-05 已追加功能补齐与真实验收，见 [最新报告](../plans/2026-10-05-query-spec-verification.md)。下文首轮耗时和模型探针保留原测量条件，不作为最新性能分位数。

## 1. 把“搜相似问题”与“列完整榜单”拆开

**可以这样讲：**

项目起初把类别枚举也走检索，用户问“前40个频率最高的算法题”时，拿到的只是有限候选，页面还可能只显示20条。我意识到这个需求首先是统计正确性问题：相似度排序不能保证全库频次排名。我让模型只判断意图和参数，完整范围的筛选、聚合、Top N 和分页交给 SQL，并保留混合检索处理语义相似查询。最终用独立 PostgreSQL 查询对照真实返回的40个题目及顺序，另外验证20加20分页无重复。

**可继续展开：**

- 聚合单位是归并题，计数单位是真实 occurrence；必须先在来源、公司、轮次等范围内筛选 occurrence，再聚合，避免一个来源的“手写”标签污染其他来源的原理题。
- 同频用 ID 稳定排序，游标绑定查询范围、用户和数据版本，数据变化明确要求刷新。
- 拆出 response_form / coding_focus，保留旧题型兼容；工程代码、算法和 SQL 不再依赖一个混合字段。
- 直接 SQL Top 40 的本轮样本为111 ms，自然语言约6.33秒。它们是两条路径的计时，不是已经证明整体系统提升了多少倍。

**证据：** [列表实现](../../src/interview_intelligence/analytics/listing.py)、[真实对照验收](../../scripts/verify-query-mvp.py)、[标注指南](../annotation-guide.md)。

## 2. Schema 合法不等于模型真的表达了完整意图

**可以这样讲：**

接入 Pi 后，我遇到一个比较隐蔽的多轮错误：用户先查工程代码，再说“只看二面”，模型有时只返回工具动作。程序默认值把缺失筛选补成了全库，形式上能执行，业务上却丢了上下文。我将模型输出和普通客户端默认参数分开，要求模型显式给出完整筛选、排序、数量及动作必需字段。缺字段先受限修复，验证通过前不执行工具。同时把查询状态保存在 PG，按钮翻页也更新当前页，这样后续的“第一题”能引用真实看到的页面。

**可继续展开：**

- 明确 null 和缺字段的区别：null 是选择不加这个筛选，缺字段是未完成计划。
- 参数校验、范围校验和允许的动作仍由宿主执行；模型没有任意 SQL / shell 工具。
- 每次规划调用一个工具，允许受预算限制的顺序读取，写操作只能终结；宿主直接返回完整事实，避免模型再次生成长列表时遗漏题目。
- request ID 绑定内容与回执；详情读取保留原列表游标；新话题重置旧 Top N。
- 在真实验收中，“只看二面”返回工程代码范围内4道题；分页后的“第一题来源”与实际第二页首题一致。

**证据：** [模型计划契约](../../src/interview_intelligence/agent/query_contract.py)、[PG 会话服务](../../src/interview_intelligence/agent/query_service.py)、[缺参数先修复的 Pi 测试](../../tests/node/pi-runtime.test.mjs)。

## 3. 开源模型毫秒级，但评测让我决定暂不接管正式路由

**可以这样讲：**

为了降低路由等待，我调研了 Jev 风格开源方案，并在 L20 自托管了 Laya Multilingual。它一组10个决策的推理中位只有19.415毫秒，但中文业务测试20个用例仅1个全部关键字段正确，65个关键字段答对29个。集成时还发现，公司选项太多会被固定问题头预算合并，所以我增加截断和候选完整性检查，把新公司实体解析交回 Pi。最终保留可替换决策接口与影子模式，正式查询继续用 Pi；先用业务评测决定是否启用，速度不能替代正确性。

**可继续展开：**

- 服务 ready 只说明模型加载与预热成功，不代表领域能力可用。
- 初次候选丢失导致422，属于集成失败；修正输入后再单独统计模型分类成绩。
- 此次没有高置信错误，但所有字段均达0.85阈值的用例也为0；不能借此声称有可用的高质量快路径，confidence 尚未领域校准。
- GPU 推理时间与包含网络、排队、2秒间隔和数据库的页面时间分开记录。
- p95 使用 nearest-rank；20个样本的20.32 ms不能外推为生产 SLA。部署对象是开源 Laya，不能称为官方 Jev。

**证据：** [固定模型与原始评测](../../evals/query-routing/results/laya-l20-20261004.json)、[输入完整性检查](../../services/jev-gateway/laya_server.py)、[质量回退](../../src/interview_intelligence/agent/jev.py)。

## 4. 工程追问：证据、计时与并发

| 面试官可能追问 | 实际可以讲的内容 |
| --- | --- |
| 标签回填为什么反复失败？ | 早期让模型复写 UUID、引用和标签，实际出现错误枚举、引用改写；v4只输出序号与标签，宿主关联 ID、原文和 hash，完整校验后原子提交。来源绑定与标签语义质量是两件事。 |
| 处理完成就代表分类正确吗？ | 2,771次全部处理，2,703次明确、68次 UNKNOWN；人工金标仍未完成，页面提示未知数量。 |
| 如何定位耗时？ | 拆队列、串行间隔、provider、规划和工具；Pi内部HTTP回调要显式恢复请求和run上下文，否则 ContextVar 不会跨网络自动传播，工具内模型计时会漏掉。 |
| 锁为什么还有竞争？ | Windows空锁文件的首字节原来在加锁前初始化，多进程时偶发 PermissionError；共享元数据初始化也移入临界区。真实API / worker仍使用同一个Linux模型锁。 |
| vendoring Pi 遇到什么？ | GitHub源码快照缺生成模型目录资源，补齐同版本npm资产并记录hash；业务逻辑放自身hooks，固定源码保持原样，离线构建只消费需要的三个包。 |
| 本地测试通过为什么还要真实服务验收？ | 实际PG聚合返回Decimal、内部HTTP上下文缺失等差异在集成路径暴露；用独立SQL、真实provider / ES和浏览器分别验证，不用SQLite样本页面代替真实结果。 |
