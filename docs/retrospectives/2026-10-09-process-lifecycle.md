# PIT-012：服务健康过，不代表离开终端或休眠后还能工作

[返回踩坑索引](README.md)

## 30 秒回忆

- **症状**：本地页面突然断开、多个容器一起重启，或唤醒后任务长期停在 RUNNING。
- **原因**：容器、发行版、WSL VM、Windows 会话的生命周期不同；有限时长或终端附属保活会结束。
- **处理**：本地启动器用按需运行的 Windows 计划任务持有无限期 WSL 会话；API 用 `exec` 接收停止信号。
- **记住**：保活、停止信号、休眠后网络恢复是三个检查点；短时存活不能证明无人值守运行。

本篇只复盘本地运行环境，不把服务器权限、模型质量或任务恢复规则归成保活故障。
任务的持久化恢复仍以数据库状态为准，保活不是恢复协议。

## 做过的处理与弯路

| 实际尝试 | 结果与留下的教训 |
| --- | --- |
| 恢复 WSL/Docker，并创建固定 `/opt` 项目链接 | 当时恢复访问；不能解决保活所属进程结束的问题 |
| 加 `restart: unless-stopped` | 容器重启策略已有，但 WSL 自身仍可能退出 |
| 运行两小时、再改六小时的 sleep | 暂时稳定，到期和交接空窗仍发生故障；延长时长只推迟退出 |
| 改成终端里的 `sleep infinity` | 取消自身到期，但仍依赖终端/执行会话寿命 |
| WMI 直接创建进程、新隐藏控制台 | 10-09 验收中仍退出，没有作为最终保活实现 |
| Windows 计划任务托管隐藏保活 | 10-09 短时脱离终端验收通过；当前脚本保留该实现 |
| 休眠故障后重启 worker | 失败任务进入恢复流程，复用已验证抽取缓存继续去重；不是自动唤醒恢复证明 |
| API 外层 shell 改为 `exec uvicorn` | 主服务接收停止信号；只延长停止超时没有解决信号转发 |

#48 中还发生过先发信号、随后 Compose 停止时被重启策略拉起一次。
这是当时确认具体进程后的处置记录，不应抄成日常“先杀进程”的操作步骤。
当前应使用受控容器生命周期命令，并先确认运行任务和影响范围。

## 当前源码里的防线

[`start-local.ps1`](../../scripts/start-local.ps1) 由项目路径与发行版计算任务名，复用同一任务。
它检查已有任务的动作、工作目录、用户、权限、运行时限和触发器，不悄悄接管异配置任务。
任务是当前用户 `Interactive / Limited`，无限执行时间、`IgnoreNew`，没有登录触发器。
隐藏 PowerShell 执行 [`wsl-keepalive.ps1`](../../scripts/wsl-keepalive.ps1)，后者持有 `sleep infinity`。
这不是 Windows 服务，也没有自动重启失败保活进程或恢复休眠后连接的循环。

启动器经 `wslpath` 定位当前工作区，当前路径不再依赖旧固定 `/opt` 链接。
它等待 Compose 就绪后从 Windows 请求 `/api/health`，并检查计划任务仍为 Running。
[`compose.yaml`](../../compose.yaml) 的 API 命令是迁移成功后 `exec uvicorn`；worker 是直接执行 Python。
容器重启策略、健康检查与计划任务分别解决不同层次的生命周期问题。

## 验证结果与未解决部分

- `resolution: mitigated` 限定为本地保活托管与 API 停止信号；休眠后自动恢复仍未由本篇关闭。
- [10-09 部署报告](../verification/2026-10-09-local-deployment.md) 记录约 96 秒的终端脱离检查。
- 当时停止多余保活，等待期间不执行 WSL 命令，只从 Windows 检查 HTTP 与计划任务，避免探针自己唤醒发行版。
- 当时五服务运行、四个健康检查正常；worker 没有独立 healthcheck，不能改写成五个均 healthy。
- 该检查不覆盖整夜、注销、Windows 重启、休眠/唤醒、网络切换与持续负载。
- 当前源码仍保留上述托管和 `exec` 实现，但本次仅核对文件，未验证今天服务在线。
- `tests: []` 表示本篇没有找到专门覆盖 Windows 任务生命周期的自动化回归入口。

## 防复发与再遇到时的排查顺序

1. 先记录 Windows 时间、VM uptime、发行版状态、容器启动时间，区分 VM、发行版、单容器和单请求。
2. 看保活任务状态与退出结果；检查宿主是否休眠、用户是否注销，不先把健康接口失败归为模型故障。
3. 若容器健康但任务无进度，核对任务阶段、最近模型调用、worker 日志与实际连接；保留停滞证据。
4. 若替换容器卡住，检查 PID 1 与停止信号链；不要把扩大超时当成确认修复。
5. 完成恢复后观察实际任务推进和持久化结果；不要仅凭页面重开就宣布恢复完整。

## 回顾自测

1. 容器有 `unless-stopped`，为什么两小时后页面仍可能消失？
2. 终端脱离 96 秒成功，能否证明 Windows 休眠后 worker 会自动继续？

答案要点：容器重启策略依赖宿主运行，有限保活还会退出；短时保活没有覆盖休眠后的连接和任务恢复。
