# 2026-10-14 字节算法题频次查询：超时误报与排序修复

## 现象和定位

正式站点输入“字节跳动算法题，按照出现频率排名”后显示“本次问答未完成／查询超时，请重试”。对应 run `e71a5199-045a-46cb-812b-3e6997cac680` 是**新会话第 1 轮**，北京时间 14:07:37 创建，14:09:24.958 已持久化为 `SUCCEEDED`，网页在 14:09:29 仍发出取消请求。服务端耗时约 107.3 秒，其中重排约 90.4 秒。服务端结果保留了 20 道题，但频次开头为 2、1、2，回答还称“按相关度排列”。

原因有两处。网页脚本的固定 110 秒截止早于服务端 180 秒查询上限，截止时不核对已保存的任务状态；本次完成事件为何没有及时到达浏览器尚无浏览器侧传输证据。算法题由 `SEARCH` 做语义核验，原查询服务没有在核验后的结果上执行用户要求的频次排序。会话轮数不是原因。

## 修复

- 网页等待上限调到 210 秒，事件流打开时每 8 秒读取持久化状态；截止时先读完任务事件并核对状态，只在确认仍 `RUNNING` 时取消。每次状态读取最多等 12 秒，避免挂起请求让截止检查无限等待。断线恢复、状态轮询和截止检查共用顺序读取，避免重复完成。
- `SEARCH` 保留算法题语义核验，频次请求先取最多 50 个检索候选，对核验结果按当前筛选范围的真实 `occurrence_count` 降序稳定排序，再截取页面。回答、警告和 `frequency_ranking` 明确这是**本次候选池内排序**。`result_selection_policy` 记录最终频次排序，原检索策略保留为 `retrieval_selection_policy`；显式“不要按频率排名”不强制频次排序。历史重查与继续找题继承正向排序要求。

## 验证与发布

网页测试 59/59 通过，覆盖 SSE 静默但已保存成功、截止核对、临时读取失败、永久挂起、断线恢复和取消边界。查询与历史重查测试在工作区 24/24 通过；同一组测试在冻结的生产包加单文件覆盖上也为 24/24，两个数字测试范围重叠。候选包 Python/Node 语法检查通过。

发布前用隔离 owner 和相同个人模型跑原句，107.39 秒返回 20 道，前十个频次为 2、2、1、1、1、1、1、1、1、1；规划为 `SEARCH`，语义核验、来源、排序和候选范围检查全部通过。首轮正式 HTTPS/SSE 验收返回 20 道、21 个 SSE 事件以 `completed` 结束，20/20 检查通过。最终版本正式 HTTPS/SSE 再跑原句返回 16 道、21 个事件以 `completed` 结束，21/21 检查通过；前十个频次仍为 2、2、1、1、1、1、1、1、1、1，持久状态 `SUCCEEDED`，模型侧总耗时约 101.2 秒。两次语义核验数量分别为 22 和 16，实际返回数量会随模型核验结果变化，不将 20 作为固定数量承诺。两次公网测试均清除了隔离账号的模型配置、admission 与 session，原账号配置摘要未变。
