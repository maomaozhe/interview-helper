<details><summary>volatile计数与统计</summary>

Java服务用volatile int count记录请求数，20个线程各执行10000次count++，全部join后count经常小于200000。为什么volatile没有解决问题？如果一个场景要求更新及并发读取严格反映单个原子计数值，另一个场景只是高并发监控统计，你分别会选什么实现并说明代价？ 请用一般技术知识直接回答，不需要查询题库。中文回答不超过400字；必要时可使用简短Java或SQL伪代码。

**原模型**

参考解答（模型知识）：

`volatile`只保证可见性和禁止相关重排序，不保证复合操作原子性。`count++`实际是：读取count → 加1 → 写回。多个线程可同时读到相同旧值，再各自写回，更新被覆盖，所以结果小于200000。

1. 严格原子计数：用`AtomicInteger`/`AtomicLong`：
```java
AtomicLong count = new AtomicLong();
count.incrementAndGet();
long v = count.get();
```
代价是每次CAS有原子指令和竞争重试开销；高竞争下可用`LongAdder`，但它不适合要求随时读到唯一精确总值的场景。

2. 高并发监控统计：优先`LongAdder`：
```java
LongAdder counter = new LongAdder();
counter.increment();
long v = counter.sum();
```
它把计数分散到多个Cell，写竞争小、吞吐高；代价是`sum()`需汇总，占用更多内存，读到的是某一时刻汇总值，不提供严格单一原子线性一致读数。若还要周期落库，可异步批量采样。

**Qwen**

volatile关键字在Java中用于确保变量的可见性，但它不能保证操作的原子性。count++操作实际上包含三个步骤：读取变量、执行加法、写回变量。这三个步骤不是原子操作，因此在多线程环境下可能导致数据不一致。为了确保原子性，可以使用AtomicInteger类，它基于CAS（Compare and Swap）操作实现线程安全的计数。对于高并发监控统计场景，可以使用Redis的计数器，它具有良好的性能和分布式支持。

</details>

<details><summary>阻塞线程池与拒绝策略</summary>

8核Java服务用Executors.newFixedThreadPool(8)处理平均耗时200ms的阻塞外部调用，入口持续500次/秒，队列和延迟不断增长。每个HTTP请求必须及时得到成功或明确失败，不能在接收请求的线程中执行这段长任务，也不能让Future永久悬挂。你会如何调整线程池、排队和拒绝策略？说明容量判断依据及至少一种不适合此约束的拒绝策略。 请用一般技术知识直接回答，不需要查询题库。中文回答不超过400字；必要时可使用简短Java或SQL伪代码。

**原模型**

参考解答（模型知识）：

按 Little 定律，阻塞调用所需在途并发约为：500 请求/秒 × 0.2 秒 = 100。8 个线程理论上限仅 40 次/秒，因此队列必然持续增长；仅靠加大无界队列是在制造延迟和内存风险。

调整：
1. 线程数按外部调用连接池、下游限流和实测RT设置，例如核心/最大线程约100，并预留CPU、GC和连接容量；HTTP连接池也要匹配，不能线程多但连接不足。
2. 使用有界队列，长度按可接受等待时间估算：若排队超时100ms，则约可放 500×0.1=50 个，结合峰值和超时取小值。
3. 入口提交任务后用带超时的获取，禁止无限等待：
```java
Future<Result> f = pool.submit(task);
try { return f.get(deadline-left, MS); }
catch(TimeoutException e){ f.cancel(true); return FAIL_FAST; }
```
4. 拒绝策略用 CallerRuns 并不合适：会阻塞接收请求线程，破坏“不能在接收线程执行长任务”，还会形成背压拖垮入口。也不要用无界队列+默认Abort之外的静默丢弃。更适合自定义拒绝：立即返回明确失败/限流响应，并记录指标；或对可中断任务取消超时任务。
5. 必须监控队列长度、拒绝数、等待时间、RT、下游错误，按P99和容量压测校准；若长期需求超过下游能力，应扩容/限流/降级，而不是堆队列。

**Qwen**

在8核Java服务中使用Executors.newFixedThreadPool(8)处理平均耗时200ms的阻塞外部调用，入口持续500次/秒，队列和延迟不断增长。每个HTTP请求必须及时得到成功或明确失败，不能在接收请求的线程中执行这段长任务，也不能让Future永久悬挂。我会调整线程池、排队和拒绝策略如下：

1. **线程池容量调整**：将线程池大小从8增加到16，以应对更高的并发需求。这样可以确保线程池能够处理更多的并发请求，减少队列积压。

2. **排队策略**：使用一个有界的队列，例如LinkedBlockingQueue，设置队列容量为1000。这样可以防止队列无限增长，同时确保请求不会被丢弃。

3. **拒绝策略**：使用一个自定义的拒绝策略，当队列满时，直接拒绝请求并返回错误信息。这样可以确保每个请求都能及时得到响应，不会在接收请求的线程中执行长任务。

**容量判断依据**：线程池的大小应根据系统的处理能力和并发需求来确定。在本例中，入口持续500次/秒，每个请求平均耗时200ms，因此需要足够的线程来处理这些请求，同时避免队列积压。

**不适合此约束的拒绝策略**：使用一个拒绝策略，如AbortPolicy，当队列满时，直接丢弃请求。这种策略不适合本场景，因为它会导致请求被丢弃，无法及时得到响应。

综上所述，调整线程池、排队和拒绝策略可以有效解决队列和延迟不断增长的问题，确保每个请求都能及时得到响应。

<details><summary>持久化及整机故障恢复</summary>

Redis当前只有每5分钟一次的RDB快照，进程崩溃后最近一段写入丢失。业务希望正常故障下丢失窗口通常控制在约1秒，并愿意付出一定写入成本。比较RDB、AOF everysec和AOF always的恢复与性能取舍，给出配置思路；如果还要求整台主机及其磁盘损坏后能恢复，还必须补什么？ 请用一般技术知识直接回答，不需要查询题库。中文回答不超过400字；必要时可使用简短Java或SQL伪代码。

**原模型**

参考解答（模型知识）：

- RDB：周期性二进制快照，文件紧凑、恢复快、对运行影响较小；但两次快照间的数据会丢，当前5分钟一次，最坏可能丢近5分钟写入。
- AOF everysec：后台每秒fsync。崩溃通常最多丢约1秒写入，性能较好，是目标场景的首选；极端操作系统/磁盘异常时可能略多。
- AOF always：每条写命令都fsync后再返回，持久性最好，基本只丢已确认失败的写，但磁盘IO会显著拖低吞吐、增加延迟。

配置思路：开启AOF并使用everysec，保留RDB作为快速全量备份/冷备；生产可让Redis 7使用Multi-Part AOF，配合aof-use-rdb-preamble混合重写，兼顾恢复速度与文件体积。根据压测调整重写阈值，避免fork和IO尖峰。示例：
appendonly yes
appendfsync everysec
save 可保留较低频RDB策略

若整台主机及本地磁盘损坏，仅本机RDB/AOF不够，还必须把AOF/RDB持续加密备份到异机、异地对象存储，并定期演练恢复；关键业务应使用主从/Redis Sentinel/Cluster，副本和备份分散在不同故障域。备份不能只放同一主机或同一磁盘。

<details><summary>旧缓存回填竞态</summary>

服务采用Cache Aside：缓存未命中时读数据库再写Redis；更新时提交数据库事务再删除缓存。读请求R先读到旧版本v0，更新请求W随后提交v1并删除缓存，最后R才把v0写回缓存。请解释问题，给出允许短暂不一致时的可实施处理方案；若某个读接口要求立即读取已提交的新值且不得读到旧缓存，方案又应如何变化？ 请用一般技术知识直接回答，不需要查询题库。中文回答不超过400字；必要时可使用简短Java或SQL伪代码。

**原模型**

问题是Cache Aside的并发回填旧值：R在W提交前读到v0，W提交v1并删缓存后，R又把过期v0写入，导致缓存长期停留在旧值，而非仅短暂不一致。

允许短暂不一致时：
1. 更新仍采用“先提交DB事务，再删除缓存”，删除失败用重试/消息队列补偿。
2. 回填设置较短TTL，并可用版本号CAS，避免旧值覆盖新值：
```java
cache.set(key, v0, TTL); // 简单方案
// 或 CAS：仅当缓存版本<=v0.version时写入
```
3. 删除缓存可用延迟双删：提交后删一次，延迟一小段时间再删；第二次删除失败仍需MQ重试。
4. 关键写路径可基于binlog订阅删除缓存，保证最终一致。

若接口要求立即读到已提交新值：该接口不能信任普通Redis读。W提交后生成单调递增版本/事务时间，读接口直接查数据库，或走强一致缓存：读时携带版本校验，发现缓存版本落后则查库并回填；W可对key加短锁/版本栅栏，未完成回填期间拒绝旧值写入。也可临时设置“禁止读缓存”标记直到新值写入完成。核心是用提交版本做CAS，旧v0不能覆盖v1。

**Qwen**

Cache Aside模式在缓存未命中时读数据库再写缓存，更新时先提交数据库事务再删除缓存。读请求R先读到旧版本v0，更新请求W随后提交v1并删除缓存，最后R才把v0写回缓存。这会导致短暂不一致，因为读请求可能读到旧缓存值。允许短暂不一致时，可采用以下方案：

1. **读请求时检查缓存是否过期**：在读取缓存前，检查缓存是否在更新后被删除，若未被删除则读取缓存，否则读数据库。

2. **使用缓存失效时间**：设置缓存的失效时间，确保在一定时间内读取到的缓存值不会过时。

若某个读接口要求立即读取已提交的新值且不得读到旧缓存，可采用以下方案：

1. **使用缓存锁**：在更新缓存时，对缓存加锁，确保读请求在更新完成后再读取。

2. **使用缓存更新后立即刷新**：在更新数据库后，立即刷新缓存，确保读请求读取到最新的缓存值。

伪代码示例：

// 更新缓存
void updateCache(String key, String value) {
    // 提交数据库事务
    submitDatabaseTransaction(key, value);
    // 删除缓存
    deleteCache(key);
    // 写入新缓存值
    writeCache(key, value);
}

// 读取缓存
String readCache(String key) {
    String value = readFromCache(key);
    if (value == null) {
        value = readFromDatabase(key);
        writeCache(key, value);
    }
    return value;
}

通过上述方案，可以确保在允许短暂不一致的情况下，读请求能够读取到最新的缓存值，同时避免读取到旧缓存值。

<details><summary>并发转账与死锁</summary>

PostgreSQL中accounts(id,balance)存放余额，在READ COMMITTED下需要把A账户100元转到B账户。请求可能与其他转账并发执行；A不能出现负余额，两边必须同时成功或同时失败。给出关键SQL或伪代码，说明如何防止并发覆盖余额，以及遇到死锁时如何处理。此题暂不考虑客户端重复提交。 请用一般技术知识直接回答，不需要查询题库。中文回答不超过400字；必要时可使用简短Java或SQL伪代码。

**原模型**

参考解答（模型知识）：

在一个事务内按固定账户顺序加行锁，用条件原子更新避免读改写覆盖；事务保证两边原子性。

```sql
BEGIN;

-- 固定 id 顺序加锁，降低死锁概率
SELECT id FROM accounts
WHERE id IN (:A,:B)
ORDER BY id
FOR UPDATE;

-- 条件扣款：余额不足则更新0行
UPDATE accounts
SET balance = balance - 100
WHERE id = :A AND balance >= 100;

-- 检查 affected rows；若为0：ROLLBACK并报余额不足

UPDATE accounts
SET balance = balance + 100
WHERE id = :B;

COMMIT;
```

要点：
1. `FOR UPDATE` 对 A、B 行加排他锁，其他并发转账必须等待，不能同时覆盖余额。
2. `balance = balance ± 100` 在数据库行上原子执行，配合 `WHERE balance >= 100` 防止透支；不要先查余额再在应用里计算后无条件写回。
3. 任一步失败或余额不足即 `ROLLBACK`，不会只扣一边。
4. 所有事务统一按账户 id 升序锁行，显著减少死锁。
5. 若仍遇到 SQLSTATE `40P01`（deadlock_detected），PostgreSQL 会自动回滚其中一个事务；应用应捕获该异常，做有限次指数退避重试，整个事务重新执行；超过次数则返回失败。

<details><summary>快照写偏差与共享约束</summary>

PostgreSQL有两名值班医生A和B，业务要求至少一人保持值班。两个REPEATABLE READ事务都查询到值班人数为2，然后分别把自己的on_call改成false并提交。为什么稳定快照仍可能使两人都下班？比较READ COMMITTED和REPEATABLE READ的读视图，再说明SERIALIZABLE及一种显式同步方案如何保护这个跨行约束。 请用一般技术知识直接回答，不需要查询题库。中文回答不超过400字；必要时可使用简短Java或SQL伪代码。

**原模型**

参考解答（模型知识）：

PostgreSQL 的 MVCC 快照只决定“能看到哪个旧版本”，不会自动校验跨行业务约束。

- REPEATABLE READ：事务开始后使用同一个稳定快照。A、B 都先看到 count=2；随后各自更新不同行。写不同行不冲突，两者都可提交，最终 count=0。
- READ COMMITTED：每条语句获取新快照。若在更新前重新 `SELECT count(*)`，后执行的事务能看到前一个已提交修改，从而发现只剩1人并中止；但普通读仍是快照读，若不重查或时序重叠，仍不能天然保证约束。
- SERIALIZABLE：SSI 会跟踪谓词读/行依赖，识别“两个事务基于同一值班集合、分别写不同行”的危险结构，让其中一个提交失败（40001），应用重试即可。

显式同步可对排班集合加锁，把检查与修改串行化：

```sql
BEGIN;
SELECT id FROM doctors
WHERE on_call
FOR UPDATE;              -- 或由触发器锁父表排班日
SELECT count(*) ...;     -- 必须 > 1
UPDATE doctors SET on_call=false WHERE id=:me;
COMMIT;
```

第二个事务会在 `FOR UPDATE` 处等待，A 提交后再读到最新状态，发现仅剩1人并回滚。

**Qwen**

在 PostgreSQL 中，REPEATABLE READ 隔离级别下，事务在读取时使用的是快照，该快照在事务开始时确定。当两个事务同时查询值班人数为 2，并分别将 on_call 改为 false 并提交时，由于快照未更新，两个事务都可能看到值班人数为 2，从而导致两人都下班。READ COMMITTED 隔离级别下，事务每次读取都使用最新的快照，因此不会出现这种情况。SERIALIZABLE 隔离级别下，事务之间相互隔离，确保一致性。显式同步方案如使用锁或事务隔离级别可以保护跨行约束。
