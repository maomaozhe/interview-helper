## 原始问题与定位

SSH 用户连续问“Redis 高频问题有哪些？”、“下一页”、“一共有多少条数据？”。第三轮沿用 Redis 范围并执行 STATS，回答“返回 20 条结果。”，把本页分组行数当成用户所问的数据总量。原始历史只读快照为 `data/reports/agent-intent-20261008/ssh-recent-turns.json`；其中还含自动化历史，不能全部当作用户真实问题。

项目已有真实 Pi Loop，但工具契约主要面向查询与复习操作；宿主用固定模板生成最终回答，没有解释、比较、题解的终结工具。会话也未保存上一轮助手回答，JSON 备用规划路径缺少实际结果行证据。因此仅调整检索关键词不能满足这次需求。

## 问题与解决记录

| 编号 | 现象或风险 | 已定位原因 | 解决与验证 |
| --- | --- | --- | --- |
| I01 | 总量问题返回 20，并错误继承 Redis | STATS 分页结果行数不是语料总量，缺少独立计数动作与全库语义 | 新增 COUNT / `get_question_count`，以 SQL 计算去重题数、提问次数、面试场次、面经篇数和已知公司数。全库问法清除上轮隐含分类，显式 UI 筛选保留。真实全库结果为 2,452 / 2,771 / 185 / 172，另有 58 家已知公司。 |
| I02 | 解释、比较、解题仍返回检索列表或模板 | 工具契约没有可生成正文的终结动作 | 新增受宿主校验的 ANSWER / `answer_question`，区分 EXPLAIN、COMPARE、SOLVE、STUDY_PLAN、CHAT；支持直接解释及 DETAILS / STATS 后继续回答。真实解释、比较和两种读后回答均通过；SOLVE、CHAT 等其余分支以自动化覆盖为准。 |
| I03 | “刚才说的…”缺少上文；“第二题”可能脱离实际题目 | 会话缺少上一回答，备用路径缺少结果行 | 保存有界 `last_response`、当前页摘要和工具证据；指代题先读取详情再作答。真实 AOF 追问与第二题 ID / 来源绑定通过。ANSWER 不覆盖原列表和游标。 |
| I04 | 计数追问可能退回旧列表范围 | 计数不应替换列表状态，但单靠最近消息无法长期保存计数范围 | 新增独立 `last_count`，保存计数筛选、复习状态与事实；“其中腾讯呢？”继承 Redis 计数范围，列表分页仍可继续。真实 Redis → 腾讯及自动化连续追问、重建服务、分页保留检查通过。 |
| I05 | 复习筛选计数可能包含已掌握题，或受其他用户状态影响 | 初版 COUNT 未应用用户复习状态 | 按当前用户和题 ID 外连接复习状态，无状态按 UNSEEN；公司、轮次等条件保持同 occurrence 语义。16 个专项用例覆盖用户隔离、缺省状态、组合筛选及重复状态不重复计数。前 N 题内数量读取 LIST 的 `result_total`，COUNT 不接受 `top_n`。 |
| I06 | 模型可能把生成解答当作题库事实 | 来源只证明题干和真实提问，不能证明模型参考解答正确 | ANSWER 标明 GENERAL_KNOWLEDGE / CORPUS / MIXED；最多引用 10 道当前页题，宿主重新读取并验证范围。无题 ID 时，题库依据必须来自本轮计数、统计或列表总量证据。越界 ID、旧轮证据和缺失依据有拒绝测试；界面显示依据说明。 |
| I07 | 分页签名与冗余元信息进入模型证据 | 原有工具回执直接投影 metadata | Context / Pi 改用字段白名单，保留数量、范围和 `has_next_page`，移除 `next_cursor`、签名结果集等不透明值。完整回执仍供宿主与界面使用。Python / Node 检查模型证据不含签名游标。 |
| I08 | 合法长中文结果导致工具成功后上下文构建失败 | 单字段虽有上限，多条题干、引文和上一回答合计仍超过 24 KB | 为可选摘要增加共享压缩预算，标记 `evidence_compacted`；保留题 ID、筛选和数量事实，不修改原始状态及回执。长中文、100 个当前页 ID、多份工具证据的边界测试通过。 |
| I09 | 初版 v11 畸形工具 JSON 修复时超预算 | 从 v10 扩展的提示约 23.7 KB，修复请求的保守字节预留与已用 token 合计触限 | 精简最终提示至 10,349 UTF-8 字节，保留路由和宿主约束；提示体积上限测试为 14 KB。最终十例全部由 Pi 完成；早期备用路径完成不算 Pi 验收通过。 |
| I10 | Redis 复习计划返回 503 / `QUERY_MODEL_BUDGET_EXCEEDED` | 首次 L1 统计只有 Redis 一个大组，模型追加读题，再生成时触及请求预算 | 暴露并持久化 `topic_level=L2`；单一大类用小类分布。默认累计请求预算由 65,536 调至 96,000，仍限 3 次规划、8 次工具和 4,096 输出 token。最终真实计划用 STATS(L2) → ANSWER 两步通过；自动化验证三步循环及回答参数修复，未验证真实三步读取后回答或做压力验收。 |
| I11 | 多段答案被压成一段；COUNT 无结果行时可能提示“没找到题” | 原渲染按题目列表和单段回答处理 | 保留转义后的纯文本换行，显示答案依据与计数范围；COUNT 不依赖题目行渲染。前端检查覆盖换行、HTML 转义、计数空行及历史回放。 |

## 开发失败和处理

以下失败先于最终十例，不纳入成功分母，也不据最终通过宣称 Provider 畸形输出已根治。最终回执单独保存在 `intent-smoke.json`；早期失败的原始日志未独立留档，以下描述依据当时开发诊断，不能用最终回执替代所有尝试的完整原始日志。

- 初版 COUNT 出现缺少对象括号的工具参数，后续修复触发 `QUERY_TOKEN_BUDGET_EXCEEDED`；一轮备用 JSON 路径虽完成 COUNT，Pi provider 断言仍失败。提示压缩后重新完整验收。
- 提示压缩后复习计划仍触及模型预算；增加 L2 统计和请求预算后重新从首例运行，未把失败轮拼入最终十例。
- 隔离 Pi 端口 18788 被其他 Python 进程占用，出现 `EADDRINUSE` 并转备用路径。检查监听后改用 18883，正式 Pi 仍使用 18787，未停止其他服务。
- 初次烟测给 `/api/agent/chat` 传 `page_size`，契约拒绝并返回 422；移除该字段，题数通过问句表达。最终脚本使用实际支持的请求字段。
- Windows 解包目录直接覆盖文件时出现 `PermissionError`；发布构建改用临时文件与原子替换，并核对最终清单。无此失败产物被发布。
- 新分页测试把同频题的随机 UUID 排序当作固定顺序，导致不稳定断言；改查第二页是第一页的精确补集且公司范围一致，保留原游标语义检查。

## 尚未关闭的问题

十例验证的是开发场景的路由、范围、事实来源和执行链路；未独立核验每段生成技术解答的正确性，不能证明所有自然语言意图均识别正确。语料里的题干与来源不会自动变成标准答案库。

**I12 / 未明确 N 时的 Top N 语义仍需修复和补验：** 首例“Redis 高频问题有哪些？”未指定数量，模型实际填了 `top_n=20`；脚本只核对 LIST 和 Pi provider，没有断言此时应使用 `top_n=null` 与分页大小20。因此本例证明列题成功，不能证明默认分页/总范围语义全部正确。后续应为未指定 N 的问法补充意图断言并验证 NEXT 可继续，再决定提示或宿主约束的修复；本轮文档更新不将此项标为已解决。

本轮没有重跑完整检索评测或 V1 六项质量门禁，H01 的误报、漏召回与已核验结果后页截断等问题仍以检索报告为准。原有取消、幂等、复习写入授权和共享模型串行限制保持；本轮也不构成生产并发或全部故障恢复验收。
