# 检索证据、召回覆盖与历史重新检索

本轮继续 [对话检索第一轮](2026-10-08-conversation-retrieval.md)，按 [补充 Spec](../plans/2026-10-08-retrieval-evidence-spec.md) 核对偏题与漏召回发生的具体层级。候选 r10 在固定 Top50 上删除了两类已知弱相关题，但更严格的对象判断也损失了业务正例；不能把返回集合变纯等同于召回全面改善。

本文记录同池实验、三轮完整 API、一次排序修复后的单场景复测，以及历史分页重检和页面验收。旧回执和旧报告保留不覆盖，超时或未达到预设验收条件的请求不计为通过。

## 测评口径与证据

在修改部署前，用上一轮保存的四条查询计划重新采集 r6 的完整 Top50、全量已接受候选和最终返回。四组返回 ID 集合与上一轮 r6 完全相同。后续 r7/r8/r9/r10 共用完全相同的候选文本、ID、相关性意图和页大小；比较脚本检查每组候选池 hash，隔离规划与召回变化。

所有返回题干由另一开发 Agent 逐条复核，裁决独立于模型给出的 grade；但复核在预测后进行，已看到结果，不是盲评、未见集或独立人工 Gold。下面仅报告**返回集合相关数/返回数**。收窄结果可提高此指标，也可能同时降低正例覆盖；没有全库 Recall。

重算脚本中的正例和负例 ID 均显式列举，未知 ID 必须再次审核，不能默认相关。冻结的原始回执受 SHA-256 校验保护，脚本只更新派生 `comparison.json`，不调用模型或改动原始预测。

## 同池实验，包括保留的失败

| 原始回执 | Agent 设计 | Harness | 秒杀业务 | 内存增长 | 结论 |
|---|---:|---:|---:|---:|---|
| before-r6 | 19/20 | 15/15 | 7/7 | 10/11 | 复现泛 AI 解说与 Full GC 两个弱相关边界 |
| after-r7 | 19/20 | 15/15 | 7/7 | 9/10 | AI 解说退出，但独立 MCP 工具交付进入；GC 仍保留，相关题被引用格式误杀 |
| after-r8 | 20/20 | 15/15 | 7/7 | 5/5 | 去掉弱题，同时漏掉五道此前相关内存题，未选用 |
| after-r9 | 20/20 | 14/15 | 7/10 | 8/8 | 泛智能复盘、通用 Redis/限流方案回潮；两个 OOM 排查题退出，未选用 |
| after-r10 | 20/20 | 15/15 | 4/4 | 10/10 | 两个原弱题退出，内存正例恢复；业务对象过严及 Harness 展示覆盖仍有损失 |

r7 的对象证据和任务证据确实来自题干，仍可能语义不匹配：Full GC 题引用“full GC 频繁”和“如何排查”，并不能证明它询问的是内存持续上涨。原文校验保证引用可核对，不保证相关性判断正确。r7 还误杀了明确的 Agent 自动修复设计和内存泄漏预防题，因此后续保留无效引用的实际片段，区分引用格式问题与语义排除。

r9 增加的三个业务弱例是通用 Redis 访问压力、先写 Redis 再异步写数据库、多机房 Redis 整体限流。它们可能出现在秒杀答案中，题干却没有目标业务对象。Harness 的泛“智能复盘、评测集指标”也需要补充题干外背景才能关联，不能计为通过。

r10 先生成题干引用，再判断对象关系及任务关系，由 host 派生 grade 并验证连续原文。普通 AI 架构、独立 MCP 工具交付、相邻故障和可能答案中的组件不会仅凭同领域获得通过。每次调用的 audit 随结果传递，避免单例 reranker 保存上一次请求状态导致串读。

固定旧池的 r10 仍有以下明确损失：

## 耗时口径

before-r6 的 `elapsed_ms` 包含 embedding、ES 和重排；after 的同池比较仅包含重排，不能直接计算同比百分比。另从 PostgreSQL `model_call` 读取 03:58:48–04:17:00 UTC 的 20 条 RERANK，每版恰好四次，按脚本固定顺序对应四组查询，获得同一操作口径：

|---|---:|---:|---:|
| r6 | 13343.5 | 11515 | 746 |
| r7 | 22632.5 | 20653.5 | 1547 |
| r8 | 34868 | 33879 | 2618 |

r10 重排耗时约为 r6 的 2.52 倍，输出 token 约为 3.45 倍；证据字段有明确成本，不能仅归因于测量范围不同。每版样本只有四个串行开发请求，Provider 波动也会影响耗时，不能外推生产分位数或费用。原始操作记录和中位数重算保存于 `comparison.json`；完整 API 端到端耗时另行留证。

完整 API 第一轮的 Harness 已出现真实 60 秒超时，原 503 回执保留。只读 PostgreSQL `model_call` 与 `agent_event` 定位为重复规划后的预算耗尽，队列等待均为 0：

| 操作 | 总耗时 ms | 串行间隔 ms | Provider ms | 状态 |
|---|---:|---:|---:|---|
| QUERY_PLAN 1 | 7379 | 1596 | 5774 | 成功返回参数，但 SEARCH top_n=15 被合同拒绝 |
| QUERY_PLAN 2 | 7744 | 1922 | 5815 | top_n 改为 50，仍被拒绝 |
| QUERY_PLAN 3 | 8014 | 1902 | 6105 | top_n=null 后进入检索 |
| EMBEDDING | 2331 | 1932 | 397 | 成功 |
| RERANK | 33598 | 1343 | 32254 | 剩余 deadline 耗尽，失败 |

三次规划先消耗约 23.1 秒；不是词法分支增加了模型调用，也不是共享门排队。`query_max_model_calls=3` 限制的是 QUERY_PLAN 次数，embedding/rerank 另外记账，不能把本轮说成总共三次模型操作。失败 run 为 `24ba829e-c76a-490d-9cc6-af19d363edf7`；两次参数拒绝分别保存于 journal sequence 9、17。合同与预算修改的重试均另留回执，未覆盖该失败。

`intent-r2` 已修正 SEARCH 的 `top_n` 合同，完整 API 中 Harness 返回 200，但业务查询又出现一次 60 秒 503。此次只读 PG 定位不同：首次 Provider 输出两个畸形 tool arguments，`filters` 中含非 JSON 文本，Pi 解析后只有 `action`，必须修复一次；两次规划分别 10896、7375 ms，embedding 4234 ms，rerank 36912 ms（Provider 35142 ms）后耗尽预算，队列等待仍均为 0。对应 run 为 `bbe5ae60-220d-4d26-8fcf-4748efceed68`，首次畸形结果在 journal sequence 5，下一规划请求 sequence 15 保留参数校验反馈。不是旧 `top_n` 错误复发，也不能据此宣称超时已彻底解决；同版本另次重试应单列。

同轮上下文查询也超时：run `06f08e01-07d8-4fed-86f9-455e6c3cfe36` 只有一次有效规划，无修复循环；规划 18478 ms、embedding 2422 ms、rerank 38633 ms，三项已经耗时 59.53 秒，正常编排开销使 60 秒预算耗尽。规划和重排的 Provider 部分分别为 16771、36967 ms，队列等待仍为 0。因此合同修正有必要，但不足以解决证据重排长度与 Provider 变化带来的延迟风险。

第三轮仍有明确残差：澄清后选择 Agent 的第二轮返回专业 AI 解说弱例，为 **19/20**，不能用直接 Agent 的 20/20 覆盖它。业务返回四道，旧不超买和订单库存正例被对象 INFERRED 降级；Redis 库存题没有进入 Top50。只读 PG 验证后者有一条符合本轮 SYSTEM_DESIGN 筛选的 active/INCLUDED/analytics_eligible occurrence，故属于候选召回缺失。Agent 另有 SDK 查询题未入池、简历助手题降级、工具可插拔题展示截断。原门禁未放宽，也没有全库 Recall 改善的结论。
